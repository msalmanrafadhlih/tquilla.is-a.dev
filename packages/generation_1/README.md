# The Typographic Journal — Dioxus port

Rust/Dioxus (web target) port of the original static HTML+Tailwind+JS
profile page. Visual output should be pixel-identical: the same Tailwind
classes, same fonts (via CDN), same layout markup — just rendered from
Rust instead of vanilla JS.

## Run it

```sh
rustup target add wasm32-unknown-unknown
cargo install dioxus-cli   # gives you the `dx` command
dx serve
```

Then open the printed local URL. This wasn't compiled or tested in the
sandbox that generated it (no Rust toolchain available there), so treat
it as a careful first draft — `dx serve` will surface any remaining
compile errors, most likely small API drift if your installed Dioxus
version differs from 0.6, or a `Dioxus.toml` key your `dx` version
doesn't recognize (safe to delete that file if so — `dx` can usually
infer the web platform from the `web` feature in `Cargo.toml` alone).

## Structure

- `index.html` — kept the original `<head>` verbatim (Google Fonts,
  Tailwind CDN + your custom `tailwind.config`), so styling behaves
  identically without needing a Tailwind build step. Dioxus mounts into
  `<div id="main">`.
- `src/data.rs` — Rust structs mirroring the `data.json` shape used by
  the original `render()` function.
- `src/util.rs` — `formatStars`, `toLocaleString`-style volume
  formatting, the rolling month-label generator, and an in-browser
  "today" (via `js_sys::Date`) used for the header date/build number and
  footer copyright year.
- `src/chart.rs` — the bezier timeline path + tooltip collision-avoidance
  logic, ported line-for-line from the JS. It builds a full `<svg>...`
  string and renders it with `dangerous_inner_html`, since `<foreignObject>`
  and `<linearGradient>` aren't typed RSX elements — this keeps the exact
  tooltip-placement algorithm (including the same fallback attempts) intact.
- `src/components.rs` — `Hero`, `ArticleCard` (shared by the two
  secondary + three tertiary pinned-repo cards), `PinnedSection`,
  `ChronicleSection` (dialects bars, stack tags, timeline), `Footer`.
- `src/main.rs` — fetches `/data.json`; if that's not being served yet,
  falls back to the bundled `data.sample.json` so the page always shows
  something. Once you point `/data.json` at real data (e.g. generated by
  a cron job the way `github-readme-card` does), it'll be picked up
  automatically — no code change needed.

## What's intentionally different from the JS version

- The dialect-bar width animation (0% → target% after 100ms) is
  reproduced with a `use_signal` + `gloo_timers` sleep instead of a raw
  `setTimeout`.
- Data loading uses `Signal<Option<AppData>>` + `use_effect(spawn(...))`
  instead of `fetch()` + manual DOM writes — everything is reactive, so
  there's no `getElementById` anywhere.
- `data.json` fallback: the original only read `window.profileData` or
  `/data.json`; this version also bundles `data.sample.json` at compile
  time as a last resort.

`data.sample.json` has placeholder numbers — swap them for real values,
or wire `/data.json` up to wherever your generator writes it.
